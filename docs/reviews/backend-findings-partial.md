## Bereich: data-model

### [high] PostgREST's 1000-row limit silently cuts off the watchlist page and the IMDb export

- **Dateien:** frontend/src/lib/watchlist.js; supabase/functions/imdb/index.ts
- **Problem:** loadWatchlist() runs `supabase.from('watchlist').select().order('added_at', {ascending:false})` with no paging (frontend/src/lib/watchlist.js:5-7). exportCsv() runs `.from('watchlist').select(...).eq('user_id', userId).order('added_at')`, also unpaged (supabase/functions/imdb/index.ts:191-195). Supabase's default API Max Rows is 1000, and the limit applies to service-role calls too. supabase/config.toml does not change it. Meanwhile the importer accepts up to 20,000 rows (imdb/index.ts:14 MAX_ROWS). export_my_data() returns a single jsonb value, so the 1000-row cap does not touch it.
- **Auswirkung:** A typical IMDb ratings export has 1,000+ titles, and Phase 3 exists to import exactly that. In that case the watchlist page shows only the 1,000 most recently added titles and gives no error. The IMDb CSV export quietly drops the oldest entries, and its 'exported'/'missing' counts (imdb/index.ts:208-209) are computed from the truncated list, so the UI reports a wrong success. Every later list (feed, notifications, list items, diary) built the same way will have the same bug.
- **Vorschlag:** (1) Frontend: page through results with keyset or `.range(from, from+999)` until a page returns fewer than 1000 rows. Or load through an RPC `my_watchlist()` that returns one jsonb array, which the row cap does not limit. Read `count: 'exact', head: true` once to show the total. (2) exportCsv: loop with `.range()` (or use an RPC returning jsonb), and limit the per-entry TMDb `external_ids` backfill (imdb/index.ts:198-204) per call so it stays within the function time limit. (3) Make it a rule in PROGRESS.md that every list query is either explicitly bounded (limit plus keyset on e.g. (added_at, tmdb_id)) or deliberately paged. Add a test that inserts 1,001 rows and checks that all of them come back.

### [high] Imports stamp watched_at with the import date; the viewing timeline is unreliable before diary and stats are built

- **Dateien:** supabase/migrations/20261012130000_data_model.sql; supabase/functions/_shared/imdb.ts
- **Problem:** watchlist_before_write sets `watched_at := now()` whenever status = 'completed' and watched_at is null (data_model.sql:31-33). mergeImportRow inserts rated IMDb titles as 'completed' with rated_at from IMDb but never passes watched_at (imdb.ts:117-125, 138). Verified with PGlite: an imported row with rated_at 2015-03-01 gets watched_at = 2026-10-12. Three more gaps: (a) switching status from 'completed' back to 'planned' keeps watched_at, and completing again keeps the first timestamp, so a rewatch cannot be recorded; (b) the rule 'rating implies rated_at' is not enforced: `update ... set my_rating = 8, rated_at = null` on a row that already had a rating leaves my_rating=8 with rated_at NULL (verified), because of the branch at data_model.sql:27-29. The import's update path can do this too, since it sets `values.rated_at = row.rated_at`, which may be null (imdb.ts:136); (c) a single watched_at column per title cannot hold the rewatch counter, 'wo/mit wem' or 52-Filme-Challenge data planned in Phases 10/11.
- **Auswirkung:** Every live IMDb import already writes hundreds of titles as 'watched today'. The year-in-review, '52 films a year', the diary and 'forgotten series' would all report that Mario watched 1,000+ films on the import date. The longer this runs, the harder it is to separate real dates from import dates.
- **Vorschlag:** Next migration: (1) In the trigger, set watched_at only when status changes into 'completed' (INSERT, or `old.status <> 'completed'`), use `coalesce(new.watched_at, new.rated_at, now())`, and fill rated_at with now() whenever my_rating is set and rated_at is null (also on UPDATE). Then add `check ((my_rating is null) = (rated_at is null))`. (2) Repair the data: `update public.watchlist set watched_at = rated_at where source = 'imdb' and rated_at is not null and watched_at > rated_at;` and mark imported dates as approximate (`watched_at_precision text check (... in ('exact','approx','unknown'))`). (3) Before Phase 10, add `viewings (id uuid pk, user_id → auth.users on delete cascade, media_type, tmdb_id, watched_on date, precision, location text check in ('cinema','home','other'), companions uuid[], note text, source, created_at)` with index (user_id, watched_on desc). Insert a viewing when status becomes completed and from imports. Treat watchlist.watched_at as a cached max(watched_on). Stats and challenges then read viewings only.

### [high] No shared title catalog: metadata is copied per user, partly written by the client, and missing what scoring, stats and streaming tools need

- **Dateien:** supabase/migrations/20261012000000_init.sql; supabase/migrations/20261012120000_watchlist_rating.sql; supabase/migrations/20261012130000_data_model.sql; DECISIONS.md
- **Problem:** Title data is stored again on each per-user row: watchlist (init.sql:34-36, watchlist_rating.sql:3-4, data_model.sql:10,14), list_items (data_model.sql:206-208), feed (data_model.sql:150-153), and series_progress (data_model.sql:93-97). The types disagree: release_date is `text` in watchlist and list_items but `date` in feed. Genre ids are stored nowhere. runtime is only filled by the IMDb import, so manual adds via search have NULL. vote_average is frozen at the moment of adding. DECISIONS.md:20 (D8) promises that shared-list titles come from the TMDb cache, but the client can insert title/poster_path/release_date on list_items (data_model.sql:388). Verified: an editor can insert title '<script>' and poster_path '../../evil', and other members see them. tmdb_cache (data_model.sql:279-285) is opaque jsonb under a text key with a TTL and gets purged, so SQL cannot join against it.
- **Auswirkung:** Planned features need per-title data that can be joined: feed scoring (genres of rated titles), 'Was schauen wir heute?' (runtime, genres), Abo-Optimierer and availability alerts (CH providers for every watchlist title, refreshed daily), stats by decade/genre/runtime, and 'Wer hat es gesehen?'. Without a catalog, each feature has to call TMDb per row on every request or parse jsonb cache blobs with concatenated keys. Caching full append_to_response payloads (credits, videos, similar) for thousands of imported titles also threatens the 500 MB free-tier database.
- **Vorschlag:** Add `public.titles (media_type text, tmdb_id int, primary key (media_type, tmdb_id), imdb_id text unique, title, original_title, original_language, poster_path, backdrop_path, release_date date, runtime int, genre_ids int[] not null default '{}', vote_average numeric(3,1), vote_count int, popularity numeric, tmdb_status text, refreshed_at timestamptz)`, plus `public.title_providers (media_type, tmdb_id, region text default 'CH', provider_id int, kind text check in ('flatrate','rent','buy','ads','free'), first_seen_at, last_seen_at, primary key (media_type, tmdb_id, region, provider_id, kind))` with an index on (provider_id, kind). RLS: authenticated may read everything; only the service role writes. Edge functions (search add, import, details, cron) upsert titles. Point watchlist, list_items and feed at it with a composite FK added `not valid` and validated after a backfill. The per-row title columns become a fallback that is no longer client-writable for list_items. Store trimmed payloads, not raw TMDb responses. Note for Phase 7: TMDb watch/providers carries no 'leaving on' date. 'Bald weg' can only be inferred from snapshot diffs (last_seen_at), so adjust that promise.

### [medium] Series tracking tables have the wrong shape for the daily cron, the 30-day calendar, spoiler protection and the binge calculator, and untracking deletes history

- **Dateien:** supabase/migrations/20261012130000_data_model.sql
- **Problem:** Show-level facts (tmdb_status, number_of_seasons/episodes, last/next_episode_to_air as jsonb) live in the per-user series_progress row (data_model.sql:90-104). Only the single next episode is stored, as jsonb. There is no episode table with air_date, runtime or name. watched_episodes has an FK to series_progress with ON DELETE CASCADE (data_model.sql:114). Verified: deleting a series_progress row deletes all of its watched episodes. series_progress is not linked to watchlist: deleting the watchlist 'tv' entry leaves series_progress orphaned (verified). watchlist.status 'watching' and the existence of a progress row are two sources of truth for the same thing.
- **Auswirkung:** The 07:15 cron would have to fetch TMDb once per (user, show) instead of once per show. A Netflix-style full-season drop shows up as one 'next episode', so the 30-day calendar and the ICS feed would be wrong. Spoiler hiding and 'at 2 episodes/day you finish on 3.11.' need every unwatched episode's name and runtime. Clicking 'stop tracking' wipes the viewing history for good. 'Vergessene Serien' has no indexed last-progress timestamp.
- **Vorschlag:** Before writing Phase 5 code, split the schema. (1) `tv_shows (tmdb_id pk, status, number_of_seasons, number_of_episodes, last_air_date date, next_air_date date, refreshed_at)` and `tv_episodes (tmdb_id, season_number, episode_number, air_date date, name, overview, runtime, still_path, primary key (...))` with an index on (air_date). Both are server-written and readable by authenticated, or this becomes part of the titles catalog. (2) Reduce series_progress to user state: `state text check in ('active','paused','dropped','finished')`, `last_progress_at` (kept up by an AFTER INSERT trigger on watched_episodes), `notify boolean`. 'Untrack' sets state instead of deleting; alternatively change the FK to ON DELETE RESTRICT. (3) The cron loops over `select distinct tmdb_id from series_progress where state = 'active'`. The calendar becomes a join of tv_episodes (air_date within the next 30 days) minus watched_episodes. (4) Add `calendar_token uuid not null default gen_random_uuid()` to user_settings for the ICS link, excluded from export like unsubscribe_token (data_model.sql:335). (5) Add `check (tmdb_id > 0)` to watched_episodes.tmdb_id (data_model.sql:109).

### [medium] Feed feedback is deleted after 30 days, and the rejection list is a racy, unbounded array

- **Dateien:** supabase/migrations/20261012130000_data_model.sql
- **Problem:** purge_expired() runs `delete from public.feed where expires_at < now()` regardless of status (data_model.sql:287-291). Verified: a 'disliked' row is gone after the purge. The only other place negative signals are kept is taste_profile.rejected_ids text[] (data_model.sql:127). The client can write it (data_model.sql:371-372) while the server job also writes it, so each side does a whole-array read-modify-write and can lose the other's update. It has no size limit (verified: 200,000 entries accepted), and its 'movie:603' strings cannot be joined against anything. The feed keys use `type`/`external_id text` (data_model.sql:148-149), while every other table uses `media_type`/`tmdb_id int`, so excluding watchlist or tombstoned titles needs a `::text` cast that indexes cannot serve. Feed rows have no reacted_at, so feedback carries no time information.
- **Auswirkung:** Titles disliked a month ago come back. The Phase 6 scoring loses its training signal (likes, dislikes, '+ added') exactly when it needs it. Concurrent writes to rejected_ids drop rejections without notice.
- **Vorschlag:** Add `feed_feedback (user_id → auth.users on delete cascade, media_type, tmdb_id int, verdict text check in ('like','dislike','added','hidden'), created_at, primary key (user_id, media_type, tmdb_id))`, filled by an AFTER UPDATE OF status trigger on feed and by the detail page, and never purged. Change purge to delete only `status = 'new'` rows. In feed, add `media_type` and a nullable `tmdb_id int` (keep external_id for albums), a partial index `(user_id, score desc) where status = 'new'`, plus `reacted_at`, `generated_at`, `algo_version` and `score_parts jsonb`, so the 'Begründung' can be explained and the algorithm tuned. Stop writing rejected_ids, or cap it with `check (cardinality(rejected_ids) <= 2000)`.

### [medium] Profiles, friendships and list membership cannot support Phase 9 safely as built

- **Dateien:** supabase/migrations/20261012000000_init.sql; supabase/migrations/20261012130000_data_model.sql
- **Problem:** (a) profiles can be read only by their owner (init.sql:185-186). Verified: a list member can see co-members' user_ids in list_members but cannot read their display names, and finding a friend by username (the reason for D10) is impossible. (b) profiles mixes private fields (email, is_admin) with public ones, and SELECT is granted on the whole table (init.sql:166). Widening the RLS policy for friends would therefore also expose their email addresses. (c) The friendship state machine is loose. Verified: after B declines, A deletes the row and sends a new request, so 'declined' blocks nothing. The addressee can flip accepted and declined back and forth. responded_at is set by the client and can be forged (set to 1999 in the probe; grant at data_model.sql:380). There is no 'blocked' state. (d) An owner can add any user to a list without friendship or consent (verified; policy at data_model.sql:461-462).
- **Auswirkung:** The social phase would have to loosen RLS on a table holding emails, or ship a list UI that shows UUIDs. The friend-request and list-invite flows can be used to harass users, and decline/block do not hold.
- **Vorschlag:** (1) Revoke table SELECT on profiles and re-grant only the columns (id, display_name, username, created_at). The user's own email comes from `auth.getUser()`. Add the policy 'self, accepted friends, or co-members can read' through a SECURITY DEFINER `are_friends(other uuid)` and a `shares_list_with(other uuid)` helper. (2) Add RPC `find_user_by_username(u text)`, which returns id and display_name for an exact match only, so users cannot be enumerated. (3) Add a BEFORE UPDATE trigger on friendships that allows only pending→accepted|declined, forces `responded_at := now()`, and adds a 'blocked' status that the requester cannot delete (narrow the delete policy). (4) Add `status text check in ('invited','active') default 'invited'` to list_members. Require `are_friends(user_id)` in the insert policy, let only the invitee set 'active', and count only active members in list_role().

### [medium] Shared-list lifecycle: the owner leaving destroys friends' work, and removed members' votes still count

- **Dateien:** supabase/migrations/20261012130000_data_model.sql
- **Problem:** shared_lists.owner_id references auth.users ON DELETE CASCADE (data_model.sql:188), and there is no way to transfer ownership (the owner row cannot be updated or deleted: data_model.sql:463-467). Verified: when the owner deletes their account, every item and vote that other members added is deleted. list_votes is tied to list_items and auth.users only (data_model.sql:214-224), not to membership. Verified: after B is removed from the list, B's +1 vote stays and is still summed, and B can no longer see it.
- **Auswirkung:** One friend deleting their account wipes the group's movie-night list. Vote totals in 'Was schauen wir?' include people who are no longer in the group.
- **Vorschlag:** Add an AFTER DELETE trigger on list_members that deletes that user's list_votes for the list. Change owner_id to ON DELETE SET NULL (nullable) and add a BEFORE DELETE trigger on auth.users, or extend delete_my_account(), that promotes the longest-standing editor to owner, or deletes the list only when no other member remains. Add `updated_at` to shared_lists, and `position int` and `note text` to list_items. Design the movie-night tables now (`movie_nights`, `movie_night_slots`, `slot_votes`), each tied to list membership in the same way.

### [medium] Function EXECUTE grants and broad table grants leak server-only capabilities to any logged-in user

- **Dateien:** supabase/migrations/20261012130000_data_model.sql; supabase/migrations/20261012000000_init.sql; tests/supabase-stub.sql; PROGRESS.md
- **Problem:** Supabase's default privileges grant EXECUTE on new public functions explicitly to authenticated, and the stub reproduces this (tests/supabase-stub.sql:19). The migrations revoke only `from public, anon` (data_model.sql:398-400; init.sql:173-174). Verified: `has_function_privilege('authenticated','public.purge_expired()','execute')` is true, and a normal user can run `select public.purge_expired()`, a SECURITY DEFINER delete across all users. PROGRESS.md:59 says it is server-only. watchlist has a table-wide INSERT grant (init.sql:170). Verified: a client can insert source='imdb', a backdated added_at and watched_at, and an arbitrary vote_average. A client-set source='imdb' also skips the tombstone lift. taste_profile arrays and jsonb columns have no size limit (verified: 200k elements), and every user shares the 500 MB free tier.
- **Auswirkung:** Today's damage is small. But Phases 5/6/12 will add SECURITY DEFINER cron functions (generate feed, refresh series, send digest), and with the same revoke pattern any invited friend could trigger them through `supabase.rpc()`, burning TMDb or Brevo quota or e-mailing everyone.
- **Vorschlag:** In the next migration: `alter default privileges in schema public revoke execute on functions from public, anon, authenticated;` then grant EXECUTE explicitly only to the RPCs (check_invite, delete_my_account, export_my_data, is_admin, list_role), and `revoke execute on function public.purge_expired() from authenticated`. Add a test that lists every non-trigger function in public that authenticated can execute and compares it with an allowlist, so future migrations cannot widen it silently. Replace the watchlist INSERT grant with a column list (media_type, tmdb_id, title, original_title, poster_path, release_date, vote_average, status, my_rating, rated_at, watched_at). Add `check (cardinality(...) <= N)` and `check (pg_column_size(genre_weights_movie) < 32768)` style limits on taste_profile.

### [low] Index and RLS performance hygiene: unindexed foreign keys, per-row auth.uid() and list_role(), missing indexes for upcoming queries

- **Dateien:** supabase/migrations/20261012000000_init.sql; supabase/migrations/20261012130000_data_model.sql
- **Problem:** Verified via pg_constraint: 7 foreign keys have no index that starts with their column: invites.created_by (init.sql:21), friendships.addressee_id (data_model.sql:171; incoming requests), shared_lists.owner_id (:188), list_members.user_id (:196; 'my lists'), list_items.added_by (:209), list_votes.user_id (:218), import_jobs.user_id (:249). 26 of 36 policies call bare `auth.uid()`, which Supabase's lint auth_rls_initplan flags; the recommended form is `(select auth.uid())`. list_items and list_votes policies call the SECURITY DEFINER list_role(list_id) once per row, and such functions cannot be inlined. EXPLAIN of `status = 'planned' order by added_at desc limit 50` shows a bitmap scan over all of the user's rows followed by a sort (PK only).

Add indexes for the coming access paths: watchlist `(user_id, status, added_at desc)`, `(user_id, watched_at desc) where watched_at is not null` (diary/stats) and `(user_id, rated_at desc) where my_rating is not null`. Add the feed and notification partial indexes from the findings above.

### [low] Hard-coded value lists and the tombstone rule will break new add paths; purge is never scheduled; migrations are only tested on empty databases

- **Dateien:** supabase/migrations/20261012000000_init.sql; supabase/migrations/20261012130000_data_model.sql; tests/db.js
- **Problem:** watchlist_after_insert lifts a tombstone only when `new.source = 'manual'` (data_model.sql:75). watchlist.source allows only ('manual','imdb') (init.sql:39), and import_jobs.kind only IMDb kinds (data_model.sql:250-251). Phase 10 (Letterboxd/Trakt), Phase 6 ('+' from the feed), lists, friend recommendations and the PWA share target all need new values. Whoever adds them has to decide each time whether the new value should lift tombstones, and an unclassified value silently does not. purge_expired() exists, but nothing schedules it: there is no pg_cron migration, so expired negative mappings and soon the Phase 4 details cache keep growing. tests/db.js:27-35 applies all migrations to an empty database, so data-repair migrations (like the watched_at fix above) and backfills (data_model.sql:322-323) are never tested against existing rows.
- **Auswirkung:** Re-added titles stay tombstoned or imports bring back deleted titles, depending on how a future source value is classified. The cache grows toward the 500 MB limit. A repair migration could fail on production data even though CI is green.
- **Vorschlag:** Invert the rule: lift the tombstone unless `source in ('imdb','letterboxd','trakt')` (bulk imports), and widen the CHECK once now (manual, imdb, letterboxd, trakt, feed, list, friend, share). Do the same for import_jobs.kind. Schedule cleanup in a migration: `create extension if not exists pg_cron; select cron.schedule('purge-expired', '17 3 * * *', 'select public.purge_expired()');`. Extend createDb() with an `upTo` option (apply migrations up to N, seed data, apply the rest) so repair and backfill migrations get tests against existing rows.

## Bereich: security

### [high] First-user-becomes-admin bootstrap is open to the internet, re-opens whenever profiles is empty, and can race

- **Dateien:** supabase/migrations/20261012000000_init.sql:73-101; supabase/migrations/20261012000000_init.sql:111; supabase/migrations/20261012130000_data_model.sql:306-320; docs/SETUP.md:52; DECISIONS.md:16
- **Problem:** enforce_invite() skips the invite check when `not exists (select 1 from public.profiles)` (init.sql:78-80), and handle_new_user() sets is_admin = `not exists (select 1 from public.profiles)` (init.sql:111, data_model.sql:314). The anon key and project URL are public in the Pages bundle, so anyone can call /auth/v1/signup directly. I checked three ways this goes wrong. (a) The documented window between `supabase db push` and Mario's own sign-up (SETUP.md:52, DECISIONS.md:16). (b) The gate re-opens. In a PGlite probe, the sole user called delete_my_account() and the next random sign-up with no code got is_admin = true. Mario only has to try 'Konto löschen' while alone once. ### [medium] Any friend can permanently poison the global IMDb-to-TMDb mapping that everyone's imports use

- **Dateien:** supabase/functions/imdb/index.ts:161-188; supabase/functions/imdb/index.ts:29-46; supabase/migrations/20261012130000_data_model.sql:278-285
- **Problem:** resolve() only checks that the IMDb id is in the caller's own job.not_found (index.ts:163-165).
